# CRM تیمی (پایه‌ی تیم + push + هسته‌ی CRM) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A mobile-first team CRM inside hesabdari for 3 partners + 1 employee: customer timeline, call/promise logging, assigned tasks with Web Push reminders, debtor follow-up, and leads.

**Architecture:** New tables in `api/core/schema.php` (auto-applied by `SchemaMigrator` on version bump). One router-mapped controller `CrmController` over small models (`TeamMember`, `CrmActivity`, `CrmTask`, `CrmLead`, `CrmTimeline`, `CrmAutomation`), a pure-PHP `WebPush` sender and a `CrmNotifier` that writes per-user `notifications` rows and pushes them. Scheduler tasks run automation and reminders. UI is a new main tab `#crm` (`templates/section_crm.php` + `js/crm-manager.js`) plus a customer “file” bottom sheet.

**Tech Stack:** PHP 8.3 (mysqli, openssl, curl; no composer), MySQL/MariaDB, jQuery + Bootstrap 5 RTL, existing `Api.call`, `UI.*` helpers, service worker `sw.js`.

**Spec:** `docs/superpowers/specs/2026-10-17-crm-core-design.md`

## Global Constraints
- Branch `crm-core` (from `audit-fixes`). No composer / no new libraries.
- Everything entity-scoped with `$_SESSION['current_entity_id']`; current user is `$_SESSION['user_id']`.
- Every new route in `$routes` of `api/index.php` must have a `$permission_map` entry (enforced by `tests/permissions_test.php`).
- Permissions: `use_crm` => `استفاده از CRM`, `manage_crm_team` => `مدیریت اعضای تیم CRM`.
- Everyone with `use_crm` sees all customers/leads/tasks; tasks only carry an assignee.
- Period lock does not apply to CRM rows (not financial documents). Every create/update/delete calls `log_activity($conn, 'crm_*', ...)`.
- UI text in Persian, dates shown Jalali (`UI.gregorianToPersian`), stored Gregorian; datepicker = existing `bd-datepicker`.
- Tests are CLI scripts in `tests/` using the real local DB like `tests/assets_test.php` (`expect_true`, unique `$token`, cleanup in `finally`). Run: `php tests/<name>.php`; pass = no `[FAIL]` lines.
- Bump `APP_VERSION` in `api/core/constants.php` to `2.3.0` (task 1) so the migration runs.

## Review Focus
1. Customer with no phone / several phones joined by ` / ` — `tel:` button uses the first number via the same rule as `KavenegarSms::normalizeOnePhone`; no button when none. (Task 8 UI check.)
2. Expired/invalid push subscription (404/410) must be deleted and must not stop pushes to the user’s other devices. (Task 2 + Task 3 test.)
3. Automation running twice (cron + request-trigger fallback) must not create duplicate tasks — unique `(entity_id, source, source_ref_id)` + `INSERT IGNORE`. (Task 7 test.)
4. Assigning a task to a team member who has no `user_id` (employee without login) must be refused with a clear error. (Task 4 test.)
5. Converting a lead whose customer save fails (missing nationalId) must leave the lead untouched. (Task 5 test.)

### Task 2: WebPush (pure PHP)

**Files:**
- Create: `api/core/WebPush.php`
- Test: `tests/webpush_test.php`

**Interfaces — Produces** (all static, base64url = no padding):
- `WebPush::generateVapidKeys(): array` → `['public' => b64url(65-byte 0x04||x||y), 'private_pem' => string]`
- `WebPush::encrypt(string $plaintext, string $uaPublicB64, string $authB64, ?string $asPrivateB64 = null, ?string $saltB64 = null): string` — RFC 8291 aes128gcm body (header salt|rs=4096|idlen=65|as_public then ciphertext). Optional args only for tests.
- `WebPush::vapidAuthHeader(string $endpoint, string $subject, string $publicB64, string $privatePem, int $exp): string` → `vapid t=<jwt>, k=<public>`.
- `WebPush::send(array $sub /* endpoint,p256dh,auth */, array $payload /* title, body, url */, array $vapid /* public, private_pem, subject */): array` → `['status' => int, 'gone' => bool]` (`gone` = 404 or 410). Headers: `TTL: 86400`, `Content-Encoding: aes128gcm`, `Urgency: normal`.

Key handling (non-obvious bits):
- Raw P-256 public (65 bytes) → PEM: DER = hex `3059301306072a8648ce3d020106082a8648ce3d030107034200` + raw.
- Raw private `d` (32) + public (65) → PEM (SEC1): hex `30770201010420` + d + `a00a06082a8648ce3d030107a144034200` + public.
- ECDH: `openssl_pkey_derive($uaPublicKey, $asPrivateKey, 32)`. HKDF: `hash_hkdf('sha256', ...)` per RFC 8291 §3.4 (key_info = "WebPush: info\0" || ua_public || as_public; IKM 32; CEK info "Content-Encoding: aes128gcm\0" 16 bytes; nonce info "Content-Encoding: nonce\0" 12 bytes). Record = plaintext || 0x02, `openssl_encrypt('aes-128-gcm', OPENSSL_RAW_DATA)`, append tag.
- ES256 JWT: `openssl_sign(..., OPENSSL_ALGO_SHA256)` returns DER — convert to raw 64-byte r||s (strip/left-pad each INTEGER to 32). JWT claims: `aud` = scheme+host of endpoint, `exp` = now+12h, `sub` = `mailto:` subject.

  - `encrypt('When I grow up, I want to be a watermelon', ua_public, auth_secret, as_private, salt)` equals the RFC 8291 §5 body. Copy the vector values (ua_public, auth_secret, as_private, as_public, salt, expected body) verbatim from RFC 8291 §5 / Appendix A (fetch https://www.rfc-editor.org/rfc/rfc8291 — do not type them from memory).
  - `vapidAuthHeader` output parses as `vapid t=…, k=…`; JWT header `{"typ":"JWT","alg":"ES256"}`; signature (raw→DER) verifies with `openssl_verify` against the generated public key; `aud` = `https://fcm.googleapis.com` for endpoint `https://fcm.googleapis.com/fcm/send/abc`.
  - `generateVapidKeys()['public']` decodes to 65 bytes starting `0x04`.
